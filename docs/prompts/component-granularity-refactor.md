# コンポーネント切り出し粒度の統一と共通化

frontend/src/pages/ 全画面のコンポーネント切り出し粒度を統一する。
複数画面で使い回せるものは src/components/ に昇格させる。
機能・見た目・挙動は一切変えない。純粋なリファクタリングとする。

## 切り出し基準（この基準ですべての画面を統一する）

### 画面本体（pages/<domain>/<Screen>/<Screen>.tsx）の責務

- 画面レベルの state 管理、データ取得、Socket.io リスナー登録、レイアウト合成のみ
- 目安 200 行以下。超える場合は下記基準で切り出す

### 画面ローカルへの切り出し（同ディレクトリの components/ へ）

次のいずれかを満たす JSX ブロックは子コンポーネントにする:

1. 意味のある UI 単位として名前が付く（カード、行、モーダル、フッター等）かつ 30 行を超える
2. 同一画面内で 2 回以上繰り返される
3. 自前のローカル state や複数のハンドラを持つ

逆に、上記を満たさない小さな JSX を無理に分割しない。過剰分割も粒度違反とする。

### 共通への昇格（src/components/ へ）

- 2 画面以上で使われる、または既存共通コンポーネントとほぼ同型のものは昇格する
- 配置は既存カテゴリに従う: controls / display / layout / modal
- 昇格時は既存の類似コンポーネント（QuantityControl, MenuQtyStepper, StatusBadge, BottomSheetModal 等）との統合を優先する。新規追加は統合できない場合のみ
- 1 画面でしか使わないものは昇格させない。先回りの共通化は禁止

### ロジックの扱い

- JSX を持たない純粋関数は .ts に分離する。画面固有なら画面ディレクトリ、2 画面以上で使うなら lib/ へ
- 参考: pages/group/GroupDetail/components/partitionOrderItems.ts が既存の先行例

## 進め方

### フェーズ1: 調査と計画（実装前にここで停止）

1. 全画面を調査し、基準違反を洗い出す
2. 画面横断で重複・類似 UI を検出する（見た目と props が近いものを突き合わせる）
3. 次の形式の計画表を提示して承認を待つ:

   | 画面 | 対象 | 種別（ローカル切り出し / 共通昇格 / 既存共通に統合 / ロジック分離） | 理由 |
   |------|------|------|------|

### フェーズ2: 実装（承認後）

- 1 画面 = 1 コミットで進める
- 各画面完了ごとに pnpm typecheck と pnpm --filter frontend test を通す
- 共通昇格・統合は該当する全利用箇所の置き換えまで含めて 1 コミットとする

## 制約

- 挙動・見た目を変えない。props の整理はよいが、レンダリング結果を変えない
- 文言は i18n/locales/ja.ts、色はデザイントークン、パスは ROUTES 定数の既存規約を維持する
- 切り出しに伴い純粋関数が新設・移動された場合のみテストを書く。JSX の分割自体にはテスト不要
- 触るのは frontend/src/ のみ。backend・shared には触れない
