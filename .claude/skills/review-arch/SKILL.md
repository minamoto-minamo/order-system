# システム設計レビュー（観点別並列サブエージェント）

8つの観点それぞれに専属のサブエージェント（`.claude/agents/review-*.md`）を並列起動してレビューさせ、1つの統合レポートにまとめる。各サブエージェントは自分の観点のチェック項目・出力形式を自前で持っているので、このSkillは「どれを呼ぶか」を決めて起動し、結果を集約するだけでよい。

## 観点とAgent名の対応

| 番号 | 観点名 | subagent_type |
|---|---|---|
| 1 | セキュリティ | `review-security` |
| 2 | データ整合性 | `review-data-integrity` |
| 3 | 会計・金額計算 | `review-accounting` |
| 4 | リアルタイム同期 | `review-realtime` |
| 5 | ビジネスロジック | `review-business-logic` |
| 6 | 運用・障害耐性 | `review-ops` |
| 7 | マルチテナント分離 | `review-tenancy` |
| 8 | UI/UXデザイン | `review-design` |

## 手順

### 1. 引数を解釈する

呼び出し時の引数（例: `1,7` のようなカンマ区切りの観点番号）を見る。

- 番号指定があれば、対応するAgent名だけを対象にする。
- 引数が空なら、全8Agentを対象にする。
- 指定番号が1〜8の範囲外なら、実行前にユーザーに確認する。

### 2. 対象Agentを並列起動する

対象のAgentそれぞれについて、Agentツールを1つずつ呼び出す。`subagent_type` に上表のAgent名を指定する。**すべて同じメッセージ内で同時に呼び出すこと**。逐次で呼ぶと並列にする意味がなくなる。

各Agentは自分のチェック項目・出力形式を内蔵しているので、プロンプトは「通常通りレビューしてください」程度の短い指示でよい。呼び出し元から追加でチェック項目を渡す必要はない（渡した場合はAgent側がそれを優先する設計になっている）。

### 3. 結果を集約してファイルに出力する

全サブエージェントの結果が返ってきたら、`work/review-arch-YYYY-MM-DD.md`（実行日の日付、同日再実行時は上書き）に次の構成で書き出す。`work/` はリポジトリ直下、`.gitignore` 済み。

```
# システム設計レビュー結果（YYYY-MM-DD）

`/review-arch`（全8観点 または実行対象の観点）の実行結果。

## サマリー

- Critical: N件 / High: N件 / Medium: N件 / Low: N件
- 観点ごとの件数内訳（1行ずつ）
- 複数観点にまたがって独立に指摘された問題があれば一言触れる

## チェックリスト

### 1. セキュリティ
- [ ] **1-1** [Critical|High|Medium|Low] 指摘タイトル（1行）
- [ ] **1-2** ...
...（各観点、指摘のタイトルのみを箇条書き。「問題なし」の観点はチェックリストへの記載不要）

### 2. データ整合性
- [ ] **2-1** ...
...

（以下、実行した観点番号順に8番まで）

---

## 詳細

## 1. セキュリティ

（サブエージェントの出力をそのまま、観点の番号順に連結。「問題なし」と報告された観点もここでは省略せず記載する）

## 2. データ整合性
...
```

- 指摘番号は `観点番号-観点内連番`（例: `2-1`, `2-2`）。観点番号は上表の番号と一致させる。観点内連番は指摘の重大度順（Critical→High→Medium→Low）に1から振る。
- チェックリストの指摘タイトルには番号を付け、詳細セクションの見出しにも同じ番号を付けて対応させる（例: チェックリスト `- [ ] **2-1** [Critical] メニュー削除が...` ⇔ 詳細見出し `### 2-1 [Critical] メニュー削除が...`）。
- サマリーの件数は、各サブエージェントの出力中の `**Critical**` `**High**` 等の表記を数えて集計する。
- サブエージェントの出力を詳細セクションで書き換えたり要約したりしない（見出しへの番号付与を除く）。事実に基づく指摘をそのまま転記する。
- ファイル書き込み後、チャットには全文を貼らない。サマリーとチェックリストのみを提示し、詳細はファイルパスへの参照に留める（詳細を知りたい観点があれば、ユーザーの求めに応じてその部分だけチャットに引用する）。

### 4. CLAUDE.mdへの反映を提案する（該当する場合のみ）

指摘の中に「CLAUDE.mdに書いておけば防げた・繰り返し起きている」類の問題（例: 特定の実装パターンの誤用、見落としがちな不変条件）が含まれる場合、レポート提示後にユーザーへ一言で `claude-md-improver` skill（`Skill(skill: "claude-md-management:claude-md-improver")`）の実行を提案する。個別のバグ指摘（1回限りの実装ミス）には提案しない。

## 関連する公式pluginとの役割分担

このSkillは「リポジトリ全体を観点別に読み込む設計レビュー」用。以下は対象・タイミングが異なるので使い分ける。

| Plugin/Skill | 対象 | 使うタイミング |
|---|---|---|
| `code-review` (`/code-review`) | GitHub PRの差分 | PRを出す・更新した時 |
| `pr-review-toolkit` (code-reviewer等) | 直近の変更差分 | commit前・PR作成前 |
| `security-guidance` | Edit/Write/commit時の差分 | 常時（hookで自動発火、インストール済みなら操作不要） |
| `review-arch`（本Skill） | リポジトリ全体・8観点 | 設計レビュー・定期監査・大きな機能追加後 |

差分だけを見たいなら `code-review` / `pr-review-toolkit` を使う。`review-arch` は差分に関係なくリポジトリ全体を各観点から洗い直すので、PRレビューの代わりにはならない。

## 観点の追加・変更

チェック項目を変えたい場合は、review-prompt.md ではなく該当する `.claude/agents/review-*.md` を直接編集する（一次情報はAgent定義側に移した）。新しい観点を追加する場合は、新しいAgent定義を作った上で、このSKILL.mdの対応表に行を追加する。
