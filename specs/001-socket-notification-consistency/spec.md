# Feature Specification: Socket.io切断・エラー通知の一貫性

**Feature Branch**: `001-socket-notification-consistency`

**Created**: 2026-07-18

**Status**: Draft

**Input**: User description: "設計レビューで見つかった2件のリアルタイム同期・運用系指摘を1フィーチャーとして仕様化する。対象: (1) order:complete/order:serveがガード違反時（対象注文が期待ステータスでない、グループ・セッションが会計済み等）に何もクライアントへ通知せず無言で終わる指摘(4-2)、(2) 店舗を無効化しても既存のSocket.io接続が生き続け、最大でアクセストークンの残り有効期限（既定15分）操作を継続できてしまう指摘(4-3/6-4、重複指摘)。前者は通知層の追加、後者は無効化時の接続強制切断の追加であり、根本原因も対処範囲も独立している。"

## Clarifications

### Session 2026-07-18

- Q: [F4] order:complete/order:serveのガード違反時、クライアントへの通知は既存の`error`イベント（`socket.emit('error', errorBody(...))`、`PageLayout`のトースト経由）を再利用するか、専用の新規イベントを設けるか？ → A: 既存の`error`イベント・トースト経路を再利用する。新規イベントは追加しない。
- Q: [F4] ガード違反の通知メッセージは、原因（対象外ステータス／グループ・セッション会計済み等）ごとに出し分けるか、単一の汎用メッセージにするか？ → A: 単一の汎用メッセージにする。原因ごとの出し分けは行わない。
- Q: [F4] 店舗無効化時のSocket.io強制切断は、`PUT /platform/stores/:id`で`isActive`を`false`に更新した直後、対象店舗の`store`ルーム全体に対して行うか。また店舗削除（内部で`isActive:false`更新を経由する）にも同一ロジックをそのまま適用してよいか？ → A: 相違なし。`isActive: false`への更新確定後、対象店舗の`store`ルーム全体に`disconnectSockets(true)`を適用する。店舗削除処理も同一ロジックで切断してよく、削除専用の特別扱いは不要。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - キッチン・ホールスタッフが提供状況操作の失敗に気づける (Priority: P1)

キッチン端末で「調理完了」、ホール端末で「提供完了」を操作した際、他のスタッフが既に同じ注文を処理済みだった、あるいは会計が確定していた等の理由でサーバー側が状態変更を行わなかった場合、操作したスタッフはその場で「反映されなかった」ことに気づける。画面が無反応のまま放置されることはない。

**Why this priority**: 現状は無言で失敗するため、スタッフは操作が効いたのか分からず連打・問い合わせが発生し、調理・提供漏れの見落としにもつながる。2件の指摘のうち、日常的な操作頻度が高くスタッフの業務に直接影響するためP1とする。

**Independent Test**: 同一注文明細に対して2つのキッチン端末からほぼ同時に「調理完了」を送信し、後着の操作を行った端末側に失敗が通知される（トースト等）ことを確認する。店舗無効化のシナリオとは独立に検証できる。

**Acceptance Scenarios**:

1. **Given** 注文明細が既に`ready`または`served`に変わっている、**When** スタッフ端末が`order:complete`を送信する、**Then** サーバーは状態を変更せず、操作したクライアントへ失敗を通知する。
2. **Given** 注文明細の所属グループ・セッションが会計済み（`closed`）である、**When** スタッフ端末が`order:complete`または`order:serve`を送信する、**Then** サーバーは状態を変更せず、操作したクライアントへ失敗を通知する。
3. **Given** 注文明細が正常に`pending`（または`ready`）のままで他の変化がない、**When** スタッフが調理完了（または提供完了）を操作する、**Then** 状態は正常に変化し、現状と同じ成功時の通知（`order:updated`のブロードキャスト）が行われる（回帰なし）。

---

### User Story 2 - 店舗無効化後、旧スタッフ端末が操作を継続できない (Priority: P2)

プラットフォーム管理者が店舗を無効化した直後、その時点で接続中だったスタッフ端末は、アクセストークンの残り有効期限にかかわらず、その店舗のリアルタイム操作（注文状態変更等）を継続できなくなる。

**Why this priority**: 新規接続は既に拒否されており実害は「無効化直前まで繋がっていた端末が最大15分操作を続けられる」に限定される。発生頻度も低い（店舗無効化はまれな運用操作）ため、User Story 1よりは優先度を下げP2とする。

**Independent Test**: スタッフ端末を店舗に接続した状態のまま、プラットフォーム管理者が当該店舗を無効化するAPIを呼び出し、直後にそのスタッフ端末のSocket.io接続が切断されることを確認する。User Story 1とは独立に検証できる。

**Acceptance Scenarios**:

1. **Given** スタッフ端末が店舗のSocket.io接続を確立し操作可能な状態、**When** プラットフォーム管理者がその店舗を無効化する（`isActive`を`false`に更新する）、**Then** その店舗に接続していた全スタッフ端末のSocket.io接続が強制的に切断される。
2. **Given** 店舗が既に無効化されている、**When** 無効化状態のままそのスタッフ端末が再接続を試みる、**Then** 現状と同じくハンドシェイクの時点で接続が拒否される（回帰なし）。
3. **Given** 店舗を削除する操作（内部で無効化を経由する）、**When** 削除処理が実行される、**Then** 無効化時と同様にその店舗の全スタッフ端末のSocket.io接続が強制的に切断される。
4. **Given** 無効化されていない別の店舗のスタッフ端末が接続中、**When** ある店舗が無効化される、**Then** 別店舗のスタッフ端末の接続には影響しない。

---

### Edge Cases

- ガード違反通知の対象は`order:complete`/`order:serve`を送信した本人のクライアントのみとし、同じ`store`/`group`ルームの他クライアントには通知しない（成功時の`order:updated`ブロードキャストとは異なる）。
- 未認証（ゲスト）接続からの`order:complete`/`order:serve`送信は現状通り即座に無視する（本フィーチャーの通知対象は認証済みスタッフの操作のみ）。
- 対象注文明細自体が存在しない（`storeId`不一致含む）場合も、ステータス不整合と同じ扱いで失敗通知の対象とする。
- 店舗無効化の強制切断は、無効化した店舗の接続のみに限定し、他店舗・プラットフォーム管理者自身の接続には影響しない。
- 店舗無効化から強制切断までの間に確立しようとした新規接続は、既存のホスト解決ロジックにより引き続き拒否される（本フィーチャーでの変更なし）。
- 店舗を再度有効化（`isActive: true`）した場合、強制切断は行わない（無効化への遷移時のみ切断する）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `order:complete`イベント処理は、対象注文明細が前提条件（`pending`ステータスであること、所属グループ・セッションが会計済み`closed`でないこと）を満たさず状態変更を行わなかった場合、既存の`error`イベント経路（`socket.emit('error', errorBody(...))` → `PageLayout`のトースト表示）を通じて操作元クライアントへ失敗を通知する。
- **FR-002**: `order:serve`イベント処理は、対象注文明細が前提条件（`ready`ステータスであること、所属グループ・セッションが会計済み`closed`でないこと）を満たさず状態変更を行わなかった場合、既存の`error`イベント経路（FR-001と同一方式）を通じて操作元クライアントへ失敗を通知する。
- **FR-003**: FR-001/FR-002の失敗通知は、原因（ステータス不一致／グループ・セッション会計済み／対象注文明細が存在しない）によらず単一の汎用メッセージとする。原因ごとの出し分けは行わない。
- **FR-004**: FR-001/FR-002の失敗通知は操作元クライアントにのみ送信し、`store`/`group`ルームの他クライアントには送信しない。
- **FR-005**: FR-001/FR-002は、前提条件を満たし状態変更が正常に行われた場合の挙動（`order:updated`のブロードキャスト内容・宛先）を変更しない。
- **FR-006**: プラットフォーム管理者による店舗更新処理（`isActive`を`false`へ更新する操作）は、更新確定後に対象店舗の`store`ルームへ参加している全Socket.io接続を強制的に切断する。
- **FR-007**: 店舗削除処理は、内部で店舗の`isActive`を`false`へ更新する既存の手順を経由するため、FR-006の強制切断ロジックがそのまま削除処理にも適用される。削除処理専用の追加ロジックは設けない。
- **FR-008**: FR-006の強制切断は、対象店舗の接続に限定し、他店舗の接続およびプラットフォーム管理者の接続には影響しない。
- **FR-009**: 店舗を`isActive: true`へ戻す更新では、強制切断を行わない。
- **FR-010**: 本フィーチャーの変更範囲は指摘された2件（`order:complete`/`order:serve`のガード違反通知、店舗無効化時のSocket.io強制切断）に限定する。ガード条件自体（前提条件の判定ロジック）や、店舗無効化・削除の業務フロー（プリコンディションチェック等）は変更対象に含めない。

### Key Entities *(include if feature involves data)*

- **OrderItem**: 個々の注文明細。`status`（`pending`/`ready`/`served`/`cancelled`）を持つ。`order:complete`/`order:serve`の対象。
- **Group / Session**: 注文明細が属するテーブル来店グループおよび営業セッション。`status`が会計済み（`closed`）かどうかがガード条件に使われる。
- **Store**: 店舗。`isActive`フラグを持つ。プラットフォーム管理者による無効化・削除の対象。
- **Socket接続（店舗ルーム）**: 認証済みスタッフが接続確立時に自動参加する店舗単位のルーム。店舗無効化時の強制切断対象。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `order:complete`/`order:serve`がガード違反により状態変更を行わなかったケースで、操作したスタッフ端末が失敗を検証可能な形で受け取れなかった件数がゼロになる（競合を再現する検証で確認する）。
- **SC-002**: 店舗無効化操作の直後（強制切断ロジック実行後）に、無効化された店舗の接続済みスタッフ端末がその店舗に対する操作イベントを送信できなくなる（検証で確認する）。
- **SC-003**: ガード違反が発生しない通常操作（提供状況変更、店舗の有効化・名称変更等）について、既存の成功時レスポンス・通知内容・接続維持動作に回帰がない。

## Assumptions

- 対象範囲は指摘された2件（`order:complete`/`order:serve`のガード違反時のクライアント通知、店舗無効化時のSocket.io強制切断）に限定する。
- `order:complete`/`order:serve`のガード違反時に「サーバー側の状態を変更しない（no-op）」という判断自体は、既存の設計判断（別フィーチャー`001-state-transition-race-fix`でclarify済み）を踏襲し、本フィーチャーでは変更しない。本フィーチャーが追加するのは「no-opの結果をクライアントへ通知する」という通知層のみである。
- 店舗無効化時の強制切断は、既存の`staff.ts`（ロール変更時・スタッフ削除時の`disconnectSockets(true)`）と同種のパターンを店舗単位に適用したものであり、新しい切断メカニズムを導入するものではない。
- 店舗の無効化・削除操作自体の頻度は低い（プラットフォーム管理者による稀な運用操作）ため、強制切断によるパフォーマンス上の懸念は本フィーチャーの範囲外とする。
