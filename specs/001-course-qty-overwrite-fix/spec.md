# Feature Specification: コース人数変更時の手動追加注文保護

**Feature Branch**: `001-course-qty-overwrite-fix`

**Created**: 2026-07-18

**Status**: Draft

**Input**: User description: "コース人数変更が手動追加注文を巻き込んで上書きする問題を修正する（設計レビュー指摘 High #3-1、会計・金額計算観点）。コース人数変更API（PUT /:id/course）は、コース由来の自動生成食事明細と、courseId付きで追加注文された手動明細を区別できず、後者の数量を人数比例の計算値で無条件に上書きしてしまう。実際に注文・提供された数量が消え、請求額が過小になる（静かなデータ損失・売上漏れ）。"

## Clarifications

### Session 2026-07-18

- Q: [F2] コース内商品と同一メニューの追加注文をどう扱いますか。(A) 引き続き許可した上で `OrderItem` にデータ区別フラグを追加しスキーマ変更・マイグレーションで保護する方式、(B) `POST /orders` 側で `courseId` 付き追加注文自体を禁止し曖昧な経路を塞ぐ方式（挙動制限のみ、スキーマ変更なし）→ A: (B) を採用する。現行フロントエンドはそもそも追加注文時に `courseId` を送信しておらず、この経路を許可する実用上の必要性がない。スキーマ変更・マイグレーションを避け、影響範囲を追加注文APIの入力検証のみに限定できる（影響最小化・シンプル第一を優先）。
- Q: 上記の禁止に該当するリクエストが来た場合、サーバーはどう応答すべきか。(A) リクエスト全体を明確なエラーで拒否する、(B) `courseId` を黙って無視し通常の追加注文として扱う → A: (A)。黙って無視すると呼び出し元が意図を誤認したまま気づけない。既存の `SoldOut` / `TakeoutMismatch` と同様、422エラーで明示的に拒否する。
- Q: 本機能適用前に作成された、courseId付き追加注文による曖昧な既存データへの遡及対応は必要か。(A) 遡及的なデータ移行・修正を行う、(B) 今後の新規発生のみを防止し、既存データはそのまま（対応しない） → A: (B)。現行フロントエンドの実装上、該当する本番データは実質存在しないと推定されるため、遡及対応は過剰実装（YAGNI）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 追加注文を巻き込まない人数変更 (Priority: P1)

店舗スタッフとして、コース適用中のグループでコース内商品と同じメニューを追加注文した後に人数変更を行っても、追加注文した分の数量が消えずに正しく請求に反映されてほしい。

**Why this priority**: 現状は追加注文分の数量が無条件に上書きされ、実際に提供した商品の請求が消える（売上漏れ）。会計金額の正確性に直結する最重要の不具合であり、これが直らない限り人数変更機能自体を安全に使えない。

**Independent Test**: コース適用済みグループに対し、コース内商品と同一メニューを含む追加注文を行った後に人数変更APIを実行し、追加注文分の数量が変更前の値のまま保持されていることを確認することで、単独でテストできる。

**Acceptance Scenarios**:

1. **Given** コースが適用され、コース内商品と同一メニューの追加注文が別途行われているグループ、**When** スタッフが人数変更を実行する、**Then** コース適用時に自動生成された食事明細の数量のみが新しい人数に比例して再計算され、追加注文分の数量は変更前のまま保持される。
2. **Given** 追加注文が一切行われていない、コース適用済みの通常のグループ、**When** スタッフが人数変更を実行する、**Then** 従来通りコース自動生成明細の数量が新しい人数に比例して正しく再計算される（既存動作からの回帰がない）。

---

### User Story 2 - 会計金額の整合性確認 (Priority: P2)

店舗スタッフとして、人数変更後の会計金額が、実際に注文・提供した商品の数量を正しく反映した金額になっていることを確認したい。

**Why this priority**: User Story 1 で数量の消失を防いだ結果が、会計画面・レポートに正しく反映されることまで確認して初めて「売上漏れ」問題の解消と言える。

**Independent Test**: 追加注文を含むグループで人数変更後、会計金額（合計）が「コース自動明細の再計算後数量 + 追加注文の数量」を正しく反映していることを確認することでテストできる。

**Acceptance Scenarios**:

1. **Given** コース自動明細と追加注文明細の両方が存在するグループで人数変更を行った直後、**When** 会計金額を計算する、**Then** 合計金額に追加注文分の数量が過不足なく含まれている。

---

### Edge Cases

- コース内商品と同一メニューだが `courseId` を指定せずに追加注文された明細（現行フロントエンドの通常経路）は、従来通り人数変更の対象外のままであること。
- 人数変更を連続して複数回実行した場合も、追加注文分の数量は毎回保持されること。
- 対象の追加注文明細がキャンセル済み（`status: cancelled`）の場合、人数変更の再計算対象・保護対象のいずれからも除外されること（現行の再計算対象クエリと同様）。
- コース適用中のグループに対し、コース内商品と同一メニューを `courseId` 付きで追加注文しようとした場合、リクエストは拒否され明細は作成されないこと。
- コースが適用されていないグループでは、そもそも `courseId` 付きの追加注文が既存の検証（`courseId` とグループの適用コースの一致チェック）により拒否されるため、本機能の対象外であること。
- 本機能適用前に作成された、courseId付き追加注文に由来する可能性のある既存の食事明細については遡及対応を行わず、人数変更時は従来通りの挙動（対象条件に一致すれば再計算対象になる）のままであること。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、コース人数変更時、コース適用によって自動生成された食事明細の数量のみを新しい人数に比例して再計算しなければならない。
- **FR-002**: システムは、コース人数変更時、スタッフが個別に追加注文した食事明細（コース内商品と同一メニューであっても）の数量を、意図せず上書き・消失させてはならない。
- **FR-003**: システムは、コースが適用されているグループに対し、そのコース内商品と同一メニューを `courseId` 付きで追加注文することを禁止しなければならない（自動生成明細と手動追加明細が区別不能な状態が新たに発生しないようにするため）。
- **FR-004**: 上記の禁止に該当する追加注文リクエストは、成功させず、明確なエラーでリクエスト全体を拒否しなければならない（黙って `courseId` を無視する、または一部の明細のみ拒否する、といった扱いは行わない）。
- **FR-005**: 本機能は新規に作成される食事明細のみを対象とし、本機能適用前に作成された既存の食事明細に対する遡及的なデータ修正は行わない。既存データに起因する人数変更時の挙動は現状維持とする。
- **FR-006**: コース自動生成明細に対する人数比例の再計算式（1人あたり数量 × 新しい人数）自体は変更しない。

### Key Entities *(include if feature involves data)*

- **食事明細（OrderItem）**: グループへの各注文明細。メニュー・数量・コース紐付け情報を持つ。
- **グループ（Group）**: コース適用状況・人数を管理する接客単位。人数変更操作の対象。
- **コース（Course）**: 標準メニュー構成（コース内商品と1人あたり数量）を持つ。人数変更時の再計算基準、および追加注文の禁止判定の基準。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: コース適用中グループに対し、コース内商品と同一メニューを `courseId` 付きで追加注文しようとした場合、その追加注文は明細として作成されず、明確なエラーが返る事例が100%になる（曖昧な明細が新規に発生する事例が0件になる）。
- **SC-002**: 追加注文が存在しない従来通りのケースで、人数変更後のコース自動明細の再計算結果が変更前と一致する（既存動作に回帰がない）。
- **SC-003**: `courseId` を指定しない通常の追加注文（現行フロントエンドの経路）は引き続き成功し、人数変更後もその数量が保持され、会計金額に過不足なく反映される。

## Assumptions

- 現行のフロントエンド（`GroupDetail`画面）は追加注文時に `courseId` を送信しないため、本指摘の経路は現行UI操作のみでは再現しない。今回のスコープは主にバックエンドAPIの安全性確保であり、UI変更は必要になった場合のみ追加で検討する。
- 客用ゲスト向け注文API（`customer.ts`）は常に `courseId: null` で明細を作成するため、本機能のスコープ外とする。
- コース自動明細の人数比例再計算そのもの（計算式・対象範囲がコース内商品であること）は既存の正しい仕様であり、変更しない。
- 本機能適用前に、courseId付き追加注文によって作成された曖昧な既存データが本番環境に存在する可能性は、現行フロントエンドの実装上、実質的にないと推定する。
