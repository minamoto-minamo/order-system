# Quickstart: セットメニュー機能の検証手順

実装完了後、以下の手順でエンドツーエンドの動作を確認する。

## 前提

```bash
pnpm --filter backend db:migrate   # MenuItem.isSet / SetFrame / SetFrameChoice / OrderItem.isSetCharge, setOrderItemId を反映
pnpm dev                            # frontend + backend 起動
```

管理者アカウントでログイン済みであること。ラーメン（味噌・醤油）とチャーハン（五目・海鮮）が商品として登録済みであること。

## シナリオ1: セットメニューの構成作成（User Story 1 / FR-001〜003, 010）

1. 管理画面 `/admin/products` で新規商品「ラーメンチャーハンセット」を作成し、セットメニューとして設定する（Acceptance Scenario 1-1）。
2. 「ラーメン」枠を追加し、選択肢「味噌ラーメン」「醤油ラーメン」を登録して保存する（Acceptance Scenario 1-2）。
3. 「チャーハン」枠を追加し、選択肢「五目チャーハン」「海鮮チャーハン」を登録して保存する。
4. 商品詳細を再表示し、2枠・各枠2選択肢が表示されることを確認する（Acceptance Scenario 1-3）。

**期待結果**: `GET /menus` のレスポンスに`isSet: true`と`setFrames`（2件、各2選択肢）が含まれる。

## シナリオ2: セットの注文（User Story 2 / FR-004〜006, 009, 011）

1. ホール画面からグループを開き、「ラーメンチャーハンセット」をタップし、「味噌ラーメン」「五目チャーハン」を選んで数量1で確定する（Acceptance Scenario 2-1）。
2. 注文明細の会計金額がセット価格通りであり、内訳商品の個別価格が加算されていないことを確認する。
3. 「醤油ラーメン」を品切れに設定した状態でセットを注文しようとし、「醤油ラーメン」が選択不可であることを確認する（Acceptance Scenario 2-2）。
4. 同じグループで再度セットを注文し、今度は「醤油ラーメン」「海鮮チャーハン」を選んで確定する。1回目の注文（味噌・五目）と独立した注文として記録されることを確認する（Acceptance Scenario 2-3）。
5. 数量2でセットを注文し、内訳の子明細も数量2で作成されることを確認する（Clarifications Q1）。

**期待結果**: `POST /orders`が親明細（`isSetCharge: true`）と子明細（`setOrderItemId`が親のidを指す）を同一トランザクションで作成する。枠の選択に不足があれば400エラーを返す。

## シナリオ3: 厨房・伝票への反映（User Story 3 / FR-007〜008）

1. シナリオ2で確定したセット注文後、キッチン画面を開く。
2. 「味噌ラーメン」「五目チャーハン」がそれぞれ独立した調理チケットとして表示されることを確認する（Acceptance Scenario 3-1）。
3. グループの注文履歴・伝票画面を開く。
4. 「ラーメンチャーハンセット」という単位の下に、選択された2品がまとめて表示されることを確認する（Acceptance Scenario 3-2）。

## シナリオ4: セット単位のキャンセル（Edge Cases）

1. シナリオ2で確定したセット注文の親明細をキャンセルする。
2. 内訳の子明細（味噌ラーメン・五目チャーハン）も連動してキャンセルされることを確認する。
3. （API直叩き等で）子明細単独のキャンセルを試み、409エラーで拒否されることを確認する。

## シナリオ5: 枠の選択肢商品の削除（Edge Cases）

1. 「醤油ラーメン」を商品一覧から削除する。
2. 「ラーメンチャーハンセット」の「ラーメン」枠から「醤油ラーメン」が自動的に除外され、「味噌ラーメン」のみ選択可能になることを確認する。
3. 過去に「醤油ラーメン」を選んで確定した注文明細（子明細）の内容・金額が変化しないことを確認する。

## 自動テストとの対応

- Backend unit test: 枠選択の過不足・重複バリデーション、セット価格計算（親0円クランプ不要・子0円固定）、セットキャンセルのカスケード、子明細単独キャンセルの拒否、`setFrames`全置換更新のnested write挙動。
- Frontend unit test: セット枠選択ボトムシートの選択状態管理、全枠未選択時の確定ボタン無効化、注文履歴のセット親子グルーピング（`setOrderItemId`によるインスタンス単位の絞り込み）。
- e2e（Claude側で実行）: シナリオ1〜4を通しで実行し、Socket.io経由の`menu:updated`/`order:created`/`order:cancelled`反映も含めて確認する。
