# Feature Specification: 会計・注文可否のサーバー側検証見直し

**Feature Branch**: `001-billing-order-validation`

**Created**: 2026-07-18

**Status**: Draft

**Input**: User description: "システム設計レビュー（work/review-arch-2026-07-18.md）の指摘3-2（客用注文APIの飲み放題プラン対象外商品混在時の全体拒否）をカバーするフィーチャー。会計・注文可否に関するサーバー側検証を、クライアント側のガードに依存せず一貫させる。指摘5-1（会計リクエスト時の未提供注文チェック欠如）は、同一エンドポイント（`POST /customer/groups/:id/bill`）を別設計で変更する001-state-transition-race-fix（指摘2-1/2-2/2-3のcheck-then-act対策）と重複するため、そちらへ統合済み。本フィーチャーは3-2のみを対象とする。"

## Clarifications

### Session 2026-07-18

- Q: 飲み放題プラン適用中のグループへの客用注文リクエストに、プラン対象外商品が混在した場合の挙動をどうするか（3-2）？ → A: 部分受理に変更する。スタッフ用 `POST /orders` と同じロジックに揃え、プラン対象商品のみ0円化・対象外商品は通常課金で両方登録する。全体拒否（422 `DrinkPlanMismatch`）のロジックは撤廃する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 飲み放題プラン適用中の来店客が対象外商品を含む注文を送信できる (Priority: P1)

飲み放題プランが適用されているグループの来店客が、プラン対象商品とプラン対象外商品（食事メニューなど）を1回の注文リクエストにまとめて送信した場合、サーバーはリクエスト全体を拒否せず、プラン対象商品のみ0円で・プラン対象外商品は通常価格で受理する（現状はプラン対象外商品が1件でも混在すると注文全体を拒否しており、実質的に来店客の自己注文チャネルが機能しなくなっている）。

**Why this priority**: 業務影響は大きい。来店客は「対象外商品だけを別リクエストで送る」または「スタッフを呼ぶ」という回避手段が現状も存在するが、放置すると自己注文チャネルの実効性が大きく損なわれ続ける。本フィーチャーの唯一のスコープであるため P1 とする。

**Independent Test**: 飲み放題プラン適用中のグループに対し、プラン対象商品とプラン対象外商品を混在させた注文リクエストを客用APIに送信し、両方の商品が1回のリクエストで登録され、プラン対象商品のみ0円・対象外商品は通常価格になることを確認する。

**Acceptance Scenarios**:

1. **Given** 飲み放題プラン適用中のグループ、**When** 来店客がプラン対象商品のみを注文する、**Then** 該当商品は0円で登録される（現行挙動を維持）。
2. **Given** 飲み放題プラン適用中のグループ、**When** 来店客がプラン対象外商品のみを注文する、**Then** 該当商品は通常価格で登録される。
3. **Given** 飲み放題プラン適用中のグループ、**When** 来店客がプラン対象商品とプラン対象外商品を混在させた1回のリクエストを送信する、**Then** リクエストは拒否されず、プラン対象商品は0円・プラン対象外商品は通常価格でそれぞれ登録される（スタッフ用 `POST /orders` と同じ扱い）。

### Edge Cases

- 客用の飲み放題対象外商品混在リクエストで、いずれかの商品が品切れ・テイクアウト専用等の既存バリデーションに抵触する場合、既存のバリデーション順序（品切れ→テイクアウト）を維持し、プラン整合性チェックの撤廃後も他のバリデーションはリクエスト全体に対して従来どおり適用される（プラン対象外商品の混在自体はもはや拒否理由にならないが、品切れ・テイクアウト専用は引き続き拒否理由になる）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、飲み放題プラン適用中のグループに対する客用注文リクエストにおいて、プラン対象商品とプラン対象外商品が混在していても、リクエスト全体を拒否せず、プラン対象商品を0円で・プラン対象外商品を通常価格でそれぞれ登録しなければならない（スタッフ用 `POST /orders` と同一の部分受理ロジックに揃える）。全商品がプラン対象外の場合も同様に、拒否せず通常価格で登録しなければならない。
- **FR-002**: システムは、飲み放題プラン対象商品については、スタッフ用・客用のいずれの注文経路でも0円で計上し、プラン対象外商品については通常価格で計上するという既存の価格計算ルールを維持しなければならない。

### Key Entities *(include if feature involves data)*

- **OrderItem（注文明細）**: グループに紐づく注文の1明細。飲み放題プラン対象商品は`price: 0`、対象外商品は`price: originalPrice`で登録される。
- **DrinkPlan（飲み放題プラン）**: グループに適用可能な定額飲み放題プラン。対象商品（`DrinkPlanItem`）に含まれる商品は注文時に0円で計上される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 飲み放題プラン適用中のグループで「プラン対象商品＋対象外商品混在」の注文を送信すると、100%リクエストが受理され、プラン対象商品は0円・対象外商品は通常価格で登録される。
- **SC-002**: 既存の会計・注文関連の自動テストがすべて成功し、かつ新規追加した検証項目（プラン混在時の挙動）に対するテストが成功する。

## Assumptions

- 本機能はバックエンドのAPI検証ロジックの変更が中心である。客用注文画面（`CustomerOrder.tsx`）側は、プラン対象外商品混在時の422エラーハンドリング（`DrinkPlanMismatch`）が今後発火しなくなるため、当該エラー分岐が残っていても実害はないが、`plan.md`で削除要否を確認する。
- レート制限・認証方式など客用API（`customer.ts`）の既存の保護機構（認証なし・レート制限のみ）はそのまま維持し、本機能では変更しない。
- 指摘5-1（会計依頼時の未提供注文チェック）は001-state-transition-race-fixに統合済みのため、本フィーチャーのスコープ外。
