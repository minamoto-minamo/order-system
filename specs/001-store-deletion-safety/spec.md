# Feature Specification: 店舗削除・無効化の運用安全性（F7）

**Feature Branch**: `001-store-deletion-safety`

**Created**: 2026-07-18

**Status**: Draft

**Input**: User description: "店舗削除・無効化の運用安全性（F7）: order-systemのプラットフォーム管理者向け店舗削除API（DELETE /api/platform/stores/:id）に、業務安全性のための2つの改善を行う。(1) 営業中のセッション・アクティブなグループが存在していても確認なく即座に削除できてしまう問題（プリコンディションチェックの欠如）。(2) カスケード削除トランザクションにタイムアウト設定がなく、データ量の多い店舗で削除が失敗しうる問題。システム設計レビュー（指摘6-1・6-2、Medium）に基づく。"

## Clarifications

### Session 2026-07-19

- Q: P1（営業中のセッション・アクティブグループがある場合の削除ガード）は、常に拒否する無条件ブロックにするか、force等の明示的確認フラグで上書きを許容するか？ → A: 無条件ブロック。force等の上書き手段は設けない。削除したければ先にセッションをcloseしグループを会計確定すればよい。
- Q: 現状、プラットフォーム管理画面は店舗削除APIを呼んでおらず、削除はAPI直接呼び出しのみで発生する。本フィーチャーで削除確認UIを新設するか？ → A: 対象外。バックエンドAPIの安全性確保のみをスコープとする。
- Q: P2（データ量が多い店舗での削除タイムアウト対策）は、トランザクションタイムアウト値の延長と削除処理の分割実行、どちらにするか？ → A: トランザクションタイムアウト値の延長。既存のカスケード削除ロジックを変えず、Prismaトランザクションの`timeout`オプションを増やすのみとする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 営業中の店舗を誤って削除できないようにする (Priority: P1)

プラットフォーム管理者が店舗削除操作を行おうとしたとき、その店舗で営業中のセッションや会計未確定のグループ（テーブル）が存在する場合は、システムが削除を拒否し、データが失われないようにする。

**Why this priority**: 現状は営業中でも無条件に削除でき、接続中のスタッフ端末の操作データや会計未確定の注文データが復元不能に失われる。バックアップ復元以外に救済策がなく、業務停止・売上データ消失に直結する最も重大なリスクであるため最優先。

**Independent Test**: 営業中のセッション（またはアクティブなグループ）を持つ店舗に対して削除操作を行い、削除が拒否され店舗データが削除前の状態のまま残ることを確認する。単独でテスト・デプロイ可能。

**Acceptance Scenarios**:

1. **Given** 対象店舗に `open` 状態のセッションが存在する、**When** プラットフォーム管理者がその店舗の削除を実行する、**Then** 削除は拒否され、店舗・セッション・グループ等のデータは削除前のまま保持される。
2. **Given** 対象店舗のセッションは `closed` だが、`active` または `bill_requested` 状態のグループが存在する、**When** プラットフォーム管理者がその店舗の削除を実行する、**Then** 削除は拒否される。
3. **Given** 対象店舗に営業中のセッション・アクティブなグループが存在しない、**When** プラットフォーム管理者がその店舗の削除を実行する、**Then** 削除は正常に完了する。
4. **Given** 削除が拒否された、**When** プラットフォーム管理者が結果を確認する、**Then** 拒否理由（営業中のデータが存在すること）が判別できる形で通知される。

---

### User Story 2 - データ量の多い店舗でも削除処理が失敗せず完了する (Priority: P2)

プラットフォーム管理者が、注文明細・グループ・スタッフ等のデータが長期間蓄積した店舗を削除するとき、削除処理がタイムアウトによって失敗しないようにする。

**Why this priority**: P1のガードにより「営業中でない店舗のみ削除できる」状態になった後でも、長期運用店舗はデータ量が多く、現状の削除処理は既定のタイムアウトを超えて失敗しうる。P1が塞ぐ経路を安全に通り抜けた削除操作自体の信頼性を担保するもので、P1に次ぐ優先度。

**Independent Test**: 注文明細・グループ・スタッフ等の関連データを大量に持つ店舗（既定のタイムアウトでは失敗する規模）を用意し、削除操作が失敗せず完了することを確認する。単独でテスト・デプロイ可能。

**Acceptance Scenarios**:

1. **Given** 削除対象店舗が既定のタイムアウトを超える規模の関連データを持つ、**When** プラットフォーム管理者がその店舗を削除する、**Then** 削除処理はタイムアウトエラーを起こさず完了し、関連データがすべて削除される。
2. **Given** 削除処理の途中でデータベースエラー等により削除が失敗する、**When** 失敗が発生する、**Then** 店舗は削除前の利用可能な状態（無効化されていない状態）に復元されるか、復元にも失敗した場合はその旨が運用者に判別できる形で記録される。

---

### Edge Cases

- 削除対象店舗のセッションが1件も存在しない（新規作成直後で未使用の店舗）場合、P1のガードには抵触せず削除できる。
- P1のガード判定（営業中セッション・アクティブグループの有無）と実際の削除実行の間に、新たな営業中セッション・グループが作成された場合、削除は成立させない（判定と削除は不可分に扱う）。
- P2のタイムアウト対策を講じてもなお削除が失敗する規模のデータが存在した場合、店舗は削除前の状態に復元され、失敗が判別可能な形で記録される。
- 既に無効化（`isActive: false`）されているが未削除の店舗に対する削除操作は、P1のガード対象（営業中セッション・アクティブグループの有無）として同様に扱う。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、店舗削除の実行前に、その店舗に `open` 状態のセッションが存在するかを判定しなければならない。
- **FR-002**: システムは、店舗削除の実行前に、その店舗に `active` または `bill_requested` 状態のグループが存在するかを判定しなければならない。
- **FR-003**: FR-001またはFR-002に該当するデータが存在する場合、システムは店舗削除を拒否し、既存データを一切変更してはならない。
- **FR-004**: 削除拒否時、システムはプラットフォーム管理者に対し、拒否理由（営業中のセッションまたはアクティブなグループが存在すること）を判別できる情報を返さなければならない。
- **FR-005**: FR-001〜FR-002の判定と、判定結果に基づく削除実行（または拒否）は、両者の間に他の操作が割り込んで判定結果を無効化しないよう、不可分な処理として扱わなければならない。
- **FR-006**: システムは、削除対象店舗に紐づく全関連データ（注文明細・グループ・セッション・コース・飲み放題プラン・メニュー・カテゴリ・席・スタッフ・設定等）の削除規模によらず、削除処理を完了できなければならない。
- **FR-007**: 削除処理が完了前に失敗した場合、システムは店舗を削除前の利用可能な状態に復元するか、復元にも失敗した場合はその旨を運用者が事後的に確認できる形で記録しなければならない。
- **FR-008**: システムは、削除が成功した場合と、FR-003により拒否された場合とを、呼び出し元が区別できる形で応答しなければならない。

### Key Entities

- **Store（店舗）**: 削除操作の対象。`isActive` フラグを持つ。
- **Session（営業セッション）**: 店舗単位の営業期間。`open`/`closed` の状態を持ち、`open` は営業中を意味する。
- **Group（グループ／卓）**: セッション内の来店単位。`active`/`bill_requested`/`closed` の状態を持ち、`active`・`bill_requested` は会計未確定を意味する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 営業中のセッションまたはアクティブなグループが存在する店舗に対する削除操作は、100%拒否され、データが失われない。
- **SC-002**: 営業中のデータが存在しない店舗の削除操作は、削除拒否の影響を受けず従来通り完了する。
- **SC-003**: 長期運用によりデータ量が蓄積した店舗（既存の既定タイムアウトでは失敗しうる規模）の削除操作が、タイムアウトを理由に失敗する件数がゼロになる。
- **SC-004**: 削除が拒否された場合、プラットフォーム管理者は再操作なしに拒否理由を特定できる。

## Assumptions

- 現状のフロントエンド（プラットフォーム管理画面）は店舗削除APIを呼び出しておらず、削除操作はAPI直接呼び出しのみで発生する（設計レビューの補足事項より）。本仕様はAPI（バックエンド）の安全性確保のみをスコープとし、削除確認UIの新設は対象外とする（Clarifications参照）。
- 「営業中」の判定基準は、既存の類似ガード（セッションクローズ時のアクティブグループチェック）に倣い、`Session.status === 'open'` および `Group.status in ['active', 'bill_requested']` とする。
- P1のガードは無条件ブロックとし、force等の上書き手段は設けない（Clarifications参照）。
- P2のタイムアウト対策はトランザクションタイムアウト値の延長とする（Clarifications参照）。
- 対象は既存の店舗削除API（プラットフォーム管理者専用、`DELETE /api/platform/stores/:id`）であり、店舗の無効化（`PUT` による `isActive: false` への変更のみの操作）自体の挙動は変更しない。
