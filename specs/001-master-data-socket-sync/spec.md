# Feature Specification: マスタデータ変更のSocket同期漏れ解消

**Feature Branch**: `001-master-data-socket-sync`

**Created**: 2026-07-18

**Status**: Draft

**Input**: User description: "システム設計レビュー（work/review-arch-2026-07-18.md）の指摘4-4（Category/SubCategoryの変更がSocket.io同期の対象外）と4-5（客用注文画面はメニュー品切れ等の変更をリアルタイムに受信しない）を1つのフィーチャーとして仕様化する。根本原因は共通で、マスタデータ変更がSocket.io経由で関係画面にブロードキャストされていないこと。"

## Clarifications

### Session 2026-07-19

- Q: カテゴリ・サブカテゴリの変更配信（User Story 1・4-4）は、客用注文画面（CustomerOrder）にも拡張するか？ → A: 拡張しない。スタッフ向けはカテゴリ変更（4-4）、客用は品切れ変更（4-5）のみとし、指摘のスコープに忠実に従う。客用注文画面のカテゴリ名・並び順は次回リロードまで反映されない（許容する）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 営業中スタッフ端末へのカテゴリ・サブカテゴリ変更の即時反映 (Priority: P1)

管理者が営業中にカテゴリ名・サブカテゴリ名や並び順を変更したとき、ホール・キッチン・グループ詳細など既に開いているスタッフ画面に、画面再読み込みなしで新しい内容が反映される。

**Why this priority**: 指摘4-4（Medium）。既存の`menu:*`イベントと同じ設計原則（マスタデータ変更は即時同期する）からの欠落であり、スタッフの業務画面全体に影響する。単独で価値を持ち、4-5より優先度が高い。

**Independent Test**: 2つのスタッフ端末（例: 管理画面とホール画面）を開いた状態で、管理画面からカテゴリ名を変更する。ホール画面側でページ再読み込みをせずに新しいカテゴリ名が表示されれば合格。カテゴリ・サブカテゴリの作成・削除でも同様に確認する。

**Acceptance Scenarios**:

1. **Given** スタッフがホール画面またはグループ詳細画面を開いている、**When** 別の管理者がカテゴリ名を変更する、**Then** 画面を再読み込みしなくても新しいカテゴリ名が表示される。
2. **Given** スタッフがキッチン画面を開いている、**When** 別の管理者がサブカテゴリを新規作成する、**Then** 画面を再読み込みしなくても新しいサブカテゴリが該当カテゴリの配下に表示される。
3. **Given** スタッフが画面を開いている、**When** 別の管理者が使用中でないカテゴリ・サブカテゴリを削除する、**Then** 画面を再読み込みしなくても一覧から削除される。
4. **Given** スタッフがカテゴリ・サブカテゴリの並び順を表示する画面を開いている、**When** 別の管理者が並び順（sort）を変更する、**Then** 画面を再読み込みしなくても新しい並び順で表示される。

---

### User Story 2 - 客用注文画面への品切れ変更の即時反映 (Priority: P2)

客が自分のスマートフォンで注文画面（CustomerOrder）を開いている間に、スタッフが商品を品切れに変更したとき、客の画面上でもその商品が品切れ表示に切り替わり、注文送信時までエラーに気づかない状態を防ぐ。

**Why this priority**: 指摘4-5（Low）。影響範囲は客用注文画面の1画面に限定されるが、顧客体験に直結する（送信して初めて失敗に気づく体験は避けたい）。4-1はP1の業務影響（スタッフ間の即時性）を持つため、4-5をP2とする。

**Independent Test**: 客用注文画面をブラウザで開いた状態を保ったまま、スタッフ画面から対象商品を品切れに変更する。客用画面をリロードせずに、その商品がカートに追加できない状態（品切れ表示）に変わることを確認する。品切れ解除でも同様に確認する。

**Acceptance Scenarios**:

1. **Given** 客が注文画面を開いており対象商品がカートに追加可能である、**When** スタッフが同商品を品切れに変更する、**Then** 客の画面を再読み込みしなくても同商品が品切れ表示になり、カートに追加できなくなる。
2. **Given** 客が注文画面を開いており対象商品が品切れ表示である、**When** スタッフが同商品の品切れを解除する、**Then** 客の画面を再読み込みしなくても同商品が注文可能な表示に戻る。
3. **Given** 客が対象商品を既にカートに入れている状態で、**When** スタッフが同商品を品切れに変更する、**Then** 客がその商品を含めて注文を送信しようとした場合の挙動は、既存の品切れチェック（送信時エラー）の仕様に従う（本フィーチャーはカート内商品の自動削除は範囲外）。

---

### Edge Cases

- カテゴリ変更イベント受信時、対象の画面がそのカテゴリ配下の商品を選択中（アクティブタブ表示中）だった場合、選択状態が壊れないこと（例: 削除されたカテゴリがアクティブタブだった場合は別カテゴリにフォールバックする）。
- Socket切断中に発生したカテゴリ・サブカテゴリ・品切れの変更は、再接続時の全件再取得（`fetchAll`）で最終的に反映される（本フィーチャーは再接続中の欠落補償を新設しない。既存の`connect`時再取得の仕組みに委ねる）。
- 客用ゲスト接続がまだどの配信経路にも参加する前（画面表示直後の初期化中）に品切れ変更イベントが発火した場合でも、直後のREST初期取得（`fetchAll`）で最終的に整合する。
- カテゴリ・サブカテゴリの削除イベントを受信した時点で、該当カテゴリ・サブカテゴリに属するメニューが画面上にまだ残っている場合の表示（商品側の`menu:deleted`は別途独立して届く前提とし、本フィーチャーはカテゴリ削除に伴うメニュー側の連鎖表示までは扱わない）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、カテゴリの作成・更新・削除が行われた際、その変更を同一店舗の接続中スタッフ画面へSocket経由でリアルタイムに配信しなければならない。
- **FR-002**: システムは、サブカテゴリの作成・更新・削除が行われた際、その変更を同一店舗の接続中スタッフ画面へSocket経由でリアルタイムに配信しなければならない。
- **FR-003**: カテゴリ・サブカテゴリの変更配信は、既存の`menu:created`/`menu:updated`/`menu:deleted`と同じ配信範囲（認証済みスタッフの店舗ルーム）・粒度（変更エンティティ単位）の設計に揃えなければならない。
- **FR-004**: スタッフ向け画面（ホール・キッチン・グループ詳細など、カテゴリ・サブカテゴリ一覧を表示または参照する既存画面）は、配信されたカテゴリ・サブカテゴリの変更イベントを受信し、画面の再読み込みなしで表示中の一覧・名称・並び順に反映しなければならない。
- **FR-005**: システムは、メニュー商品の品切れ状態の変更を、その商品を注文可能な画面を開いている客用ゲスト接続へリアルタイムに配信しなければならない。
- **FR-006**: 客用注文画面は、配信された品切れ変更イベントを受信し、画面の再読み込みなしで対象商品の注文可否表示（品切れ表示）を更新しなければならない。
- **FR-007**: 客用ゲストへの配信は、そのゲストが参照可能な範囲（自グループが所属する店舗）を超えて他店舗の情報を含んではならない。
- **FR-008**: カテゴリ・サブカテゴリ・品切れ変更の配信は、既存のスタッフ向けマスタデータ同期（`menu:*`等）と比べて認可・権限上の追加露出を生じさせてはならない（未認証の客用ゲストに、スタッフ限定情報を新たに公開しない）。

### Key Entities

- **Category（カテゴリ）**: メニューの大分類。`id`、`name`、`sort`、店舗ID等を持つ。既存エンティティ、変更なし。
- **SubCategory（サブカテゴリ）**: メニューの小分類。`id`、`name`、`categoryId`、`sort`、店舗ID等を持つ。既存エンティティ、変更なし。
- **MenuItem（メニュー商品）**: `soldOut`フラグを持つ既存エンティティ。本フィーチャーでは品切れ状態変更の配信先を拡張するのみで、エンティティ自体は変更しない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 営業中にカテゴリ・サブカテゴリの名称・並び順・作成・削除を変更した場合、既に開いている全スタッフ画面（ホール・キッチン・グループ詳細）に、画面操作（再読み込み等）を伴わず変更が反映される。
- **SC-002**: 営業中に商品を品切れ／品切れ解除に変更した場合、その商品を表示している客用注文画面に、画面操作を伴わず変更が反映される。
- **SC-003**: 客が品切れ商品を注文しようとして送信時エラーで初めて気づくケースが、画面を開いたまま品切れに変更された商品については発生しなくなる（事前に注文不可であることが画面上でわかる）。
- **SC-004**: 本フィーチャーの変更が、既存のスタッフ・客用ゲスト間の情報アクセス境界（客用ゲストが他グループ・スタッフ専用情報にアクセスできないこと）を壊さない。

## Assumptions

- カテゴリ・サブカテゴリ変更のスタッフ向け配信は、既存`menu:*`イベントと同じ「認証済みスタッフの店舗ルーム（`store:${storeId}`）」への配信でよく、客用ゲストへの配信は別スコープ（User Story 2）として扱う。
- 客用ゲスト接続は現在`group:${groupId}`ルームのみに参加し、`store:${storeId}`ルームには参加しない（意図的なテナント・権限分離）。この境界は本フィーチャーでも維持する前提とし、品切れ配信のために客用ゲストをスタッフの店舗ルームへ参加させることはしない。
- 客用注文画面への品切れ配信は、既存のメニュー一覧取得（カテゴリ・サブカテゴリ・メニュー・飲み放題対象商品IDをまとめて返すエンドポイント）が参照する範囲と同じ「グループが所属する店舗の全メニュー」を対象とする。
- カテゴリ・サブカテゴリの変更配信は客用注文画面には拡張しない（Clarifications参照）。客用注文画面はUser Story 2（品切れ変更）の配信経路のみ新設する。
- 本フィーチャーは配信の欠落を解消することが目的であり、配信内容（ペイロード形式）は既存の`menu:*`系イベントに倣った最小限の情報（変更後のエンティティ全体、または削除の場合はID）とする。
