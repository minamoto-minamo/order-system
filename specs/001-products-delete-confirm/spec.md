# Feature Specification: 商品管理画面の削除操作に確認ステップを追加する

**Feature Branch**: `001-products-delete-confirm`

**Created**: 2026-07-18

**Status**: Draft

**Input**: User description: "商品管理画面の削除操作に確認ステップを追加する（設計レビュー UI/UXデザイン観点、Critical、指摘番号8-1への対応）"

## Clarifications

### Session 2026-07-18

- Q: 削除ボタンは編集モーダル（`InputModal`/`ProductModal`）の内側にある。確認ステップをどう重ねるか？ → A: 編集モーダルを閉じてから確認シートを表示する。キャンセル時は編集モーダルに戻らず、両方閉じた状態にする。
- Q: カテゴリ・小分類削除時の確認文言に、配下データも失われる旨を明示するか？ → A: カテゴリ・小分類は配下データ（小分類・商品）が失われる旨を文言に追加する。商品は配下データがないため `{{name}} を削除しますか？` のみのシンプルな文言で統一する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 商品削除時に確認ステップを挟む (Priority: P1)

管理者が商品編集モーダルの「削除」ボタンをタップしたとき、即座に商品が削除されるのではなく、削除対象の商品名を明示した確認ステップが表示され、管理者が明示的に確定操作を行って初めて削除が実行される。

**Why this priority**: 商品削除は3種類の削除操作の中で最も操作頻度が高く、日常的な誤タップのリスクが最も大きい。単独でも「誤削除防止」という価値を完結して提供できる。

**Independent Test**: 商品編集モーダルを開き「削除」をタップする。確認ステップが表示され、そこでキャンセルすれば商品が削除されないこと、確定すれば削除されることを確認する。他の削除操作（カテゴリ・小分類）の実装状況に関わらず単独で検証できる。

**Acceptance Scenarios**:

1. **Given** 商品編集モーダルを開いている、**When** 「削除」ボタンをタップする、**Then** 編集モーダルが閉じ、代わりに対象商品名を含む確認ステップが表示され、商品はまだ削除されない。
2. **Given** 商品削除の確認ステップが表示されている、**When** キャンセル操作を行う、**Then** 確認ステップが閉じる（編集モーダルは再表示されない）。商品は削除されない。
3. **Given** 商品削除の確認ステップが表示されている、**When** 削除を確定する操作を行う、**Then** 商品が削除され、確認ステップが閉じる。

---

### User Story 2 - 小分類削除時に確認ステップを挟む (Priority: P2)

管理者が小分類編集モーダルの「削除」ボタンをタップしたとき、削除対象の小分類名を明示した確認ステップが表示され、明示的な確定操作を経て初めて小分類（および配下の商品のローカル表示からの一括除去）が実行される。

**Why this priority**: 小分類削除は配下の商品も連動して削除される破壊的操作だが、商品削除より発生頻度は低い。

**Independent Test**: 小分類編集モーダルを開き「削除」をタップする。確認ステップでキャンセル・確定それぞれの結果を検証する。商品削除の実装と独立して検証できる。

**Acceptance Scenarios**:

1. **Given** 小分類編集モーダルを開いている、**When** 「削除」ボタンをタップする、**Then** 編集モーダルが閉じ、代わりに対象小分類名を含む確認ステップが表示され、小分類はまだ削除されない。
2. **Given** 小分類削除の確認ステップが表示されている、**When** キャンセル操作を行う、**Then** 確認ステップが閉じる（編集モーダルは再表示されない）。小分類は削除されない。
3. **Given** 小分類削除の確認ステップが表示されている、**When** 削除を確定する操作を行う、**Then** 小分類と配下の商品が削除され、確認ステップが閉じる。

---

### User Story 3 - カテゴリ（大分類）削除時に確認ステップを挟む (Priority: P3)

管理者がカテゴリ編集モーダルの「削除」ボタンをタップしたとき、削除対象のカテゴリ名を明示した確認ステップが表示され、明示的な確定操作を経て初めてカテゴリ（および配下の小分類・商品のローカル表示からの一括除去）が実行される。

**Why this priority**: カテゴリ削除は影響範囲が最も広い破壊的操作（配下の小分類・商品すべてが連動して失われる）だが、発生頻度は3操作中で最も低い。

**Independent Test**: カテゴリ編集モーダルを開き「削除」をタップする。確認ステップでキャンセル・確定それぞれの結果を検証する。他2操作の実装と独立して検証できる。

**Acceptance Scenarios**:

1. **Given** カテゴリ編集モーダルを開いている、**When** 「削除」ボタンをタップする、**Then** 編集モーダルが閉じ、代わりに対象カテゴリ名を含む確認ステップが表示され、カテゴリはまだ削除されない。
2. **Given** カテゴリ削除の確認ステップが表示されている、**When** キャンセル操作を行う、**Then** 確認ステップが閉じる（編集モーダルは再表示されない）。カテゴリは削除されない。
3. **Given** カテゴリ削除の確認ステップが表示されている、**When** 削除を確定する操作を行う、**Then** カテゴリ・配下の小分類・配下の商品が削除され、確認ステップが閉じる。

---

### Edge Cases

- 削除確認ステップの表示中に、削除対象が他のクライアントから既に削除されていた場合（API側で404等が返る場合）、既存の `apiErrorMessage` によるエラートースト表示にフォールバックする（本機能の追加スコープ外、既存のエラーハンドリングを踏襲）。
- 確認ステップ表示中に確認シートの外側（オーバーレイ）をタップした場合、キャンセルと同様に確認ステップが閉じる操作として扱う（編集モーダルは再表示されず、削除も実行されない）。
- 選択中の小分類が削除された場合、削除確定後に選択状態を解除する（既存の `deleteSub`/`deleteCat` の挙動を維持する）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、商品削除操作（`deleteProduct`）の実行前に、削除対象の商品名を含む確認ステップを表示しなければならない。
- **FR-002**: システムは、小分類削除操作（`deleteSub`）の実行前に、削除対象の小分類名を含む確認ステップを表示しなければならない。
- **FR-003**: システムは、カテゴリ削除操作（`deleteCat`）の実行前に、削除対象のカテゴリ名を含む確認ステップを表示しなければならない。
- **FR-004**: 確認ステップにはキャンセル操作が存在し、キャンセルした場合は削除を実行せず、対象を削除前の状態のまま維持しなければならない。
- **FR-005**: 確認ステップには削除確定操作が存在し、確定した場合のみ既存の削除API呼び出し（`deleteCat`/`deleteSub`/`deleteProduct`）を実行しなければならない。
- **FR-006**: 確認ステップの文言は、削除対象の名前を埋め込んだ形式でなければならない。カテゴリ・小分類の確認文言は配下の小分類・商品が連動して失われる旨を含めなければならない。商品の確認文言は配下データがないため、削除対象の商品名を含むシンプルな確認文で足りる。
- **FR-007**: 確認ステップのボタン配置・スタイルは、リポジトリ内の既存の削除確認パターン（`frontend/src/pages/admin/Staff/Staff.tsx` の `staff.deleteConfirm` を用いた確認、`BottomSheetModal` の `secondaryAction`/`primaryAction` による確認と同種の構成）と一貫性を持たなければならない。
- **FR-008**: 削除確定操作後、既存の削除失敗時エラーハンドリング（`apiErrorMessage` によるトースト表示）は維持されなければならない。
- **FR-009**: 削除ボタンのタップ時、システムは編集モーダル（`InputModal`/`ProductModal`）を閉じたうえで確認ステップを表示しなければならない。編集モーダルと確認ステップを同時に重ねて表示してはならない。
- **FR-010**: 確認ステップでキャンセルした場合、システムは編集モーダルを再表示してはならない（確認ステップが閉じ、両モーダルとも非表示の状態に戻る）。

### Key Entities

- **カテゴリ（大分類）**: 商品を分類する最上位区分。削除すると配下の小分類・商品もローカル表示から一括除去される。
- **小分類**: カテゴリに属する下位区分。削除すると配下の商品もローカル表示から除去される。
- **商品**: 小分類に属する個別のメニュー項目。削除すると一覧から除去される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 商品・小分類・カテゴリいずれの削除操作も、確認ステップでの確定操作なしには削除が実行されない（誤タップ1回のみでは削除が完了しない）。
- **SC-002**: 確認ステップの表示から削除確定・キャンセルまでの操作は、既存のスタッフ削除確認と同等の操作手数（確認シートでの1タップ）で完了する。
- **SC-003**: 確認ステップをキャンセルした場合、削除対象は変更前と完全に同一の状態を維持する（データ・表示の両方）。

## Assumptions

- 確認ステップのUIパターンは、既存の `BottomSheetModal`（`secondaryAction`/`primaryAction` によるキャンセル・確定ボタン構成）または `ConfirmModal` 相当の仕組みを流用する前提とし、新規のモーダル基盤は追加しない。
- 確認文言は `frontend/src/i18n/locales/ja.ts` の `productSettings` 配下に追加し、既存の `staff.deleteConfirm`（`{{name}} を削除しますか？`）と同様に対象名を埋め込む形式に揃える。
- 本機能はフロントエンドのUI/UXフローの変更のみであり、バックエンドAPI（削除エンドポイント自体の挙動）の変更は伴わない。
- 対象範囲は `frontend/src/pages/admin/Products/` 配下の3種類の削除操作（カテゴリ・小分類・商品）のみとし、他画面（Staff、GroupDetail等）の既存の削除確認フローは変更しない。
