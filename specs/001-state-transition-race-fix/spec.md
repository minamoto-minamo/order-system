# Feature Specification: 状態変更エンドポイントのレースコンディションをトランザクション内再検証で解消する

**Feature Branch**: `001-state-transition-race-fix`

**Created**: 2026-07-18

**Status**: Draft

**Input**: User description: "設計レビューで見つかった3件のデータ整合性指摘（check-then-actによるレースコンディション）を1フィーチャーとして仕様化する。対象: (1) POST /customer/groups/:id/bill の会計依頼、(2) Socket.io の order:complete / order:serve、(3) POST・PUT /:id/course のコース適用・人数変更。根本原因は共通で、状態確認クエリと状態書き込みクエリが分離しており、間に他リクエストが割り込むと検証をすり抜ける。対処方針は docs/data-model/concurrency-notes.md に定義済み。"

**統合の経緯（2026-07-19追記）**: 旧001-billing-order-validationフィーチャーが対象としていた指摘5-1（会計依頼時の未提供注文チェック欠如）を本フィーチャーへ統合した。5-1と2-1（本フィーチャーのUser Story 1）はどちらも`POST /customer/groups/:id/bill`（および5-1はスタッフ用`PUT /api/groups/:id`も対象）の同一箇所を変更する別々の検証であり、実装上は同一の不可分操作内にまとめる必要があるため。001-billing-order-validationは3-2（飲み放題プラン部分受理）のみのスコープに縮小した。

## Clarifications

### Session 2026-07-18

- Q: [F1] order:complete/order:serveで競合を検知した場合、Socket.ioクライアントへエラー通知するか、現状通り無応答no-opのままにするか？ → A: 現状通りサイレントno-op。呼び出し元クライアントには何も通知しない（前提条件不一致時の既存挙動と統一）。
- Q: [F1] 会計依頼で競合を検知した場合のエラー応答は、既存の400/BillRequestNotAllowedと同じにするか、専用の409 Conflict等に変えるか？ → A: 既存の400/BillRequestNotAllowedを再利用する。新規エラーコードは追加しない。（**2026-07-19注記**: これはグループ状態競合＝`active`でなくなっていた場合の応答に限る。未提供注文チェック（5-1統合）による拒否は別の理由のため、新規409エラーコードを別途使う。下記Session 2026-07-19参照。）
- Q: [F1] 3箇所で採用する並行制御手段（Serializableトランザクション内再検証 vs updateManyによるcompare-and-swap）を統一するか、箇所ごとに選ぶか？ → A: 箇所の性質に応じて選ぶ。会計依頼と`order:complete`/`order:serve`は単一行の条件付き更新（compare-and-swap）、コース適用・人数変更は複数行の作成・更新と参照系エンティティ再取得を伴うためSerializableトランザクション内再取得（既存の`unapplyCourse`と同パターン）とする。統一するのは「確認と書き込みを不可分にする」という原則レベルにとどめる。（**2026-07-19注記**: 5-1統合に伴い、会計依頼（`customer.ts`/`groups.ts`）はcompare-and-swapからSerializableトランザクション内再検証に変更する。未提供注文チェック（`OrderItem`の集計）は別テーブルの条件であり、`updateMany`の`where`句だけでは表現できないため。`order:complete`/`order:serve`は影響を受けず、引き続きcompare-and-swapのまま。）

### Session 2026-07-19（旧001-billing-order-validationより統合）

- Q: 未提供（`pending`/`ready`）の注文明細が残っているグループへの会計依頼を、サーバー側でどう扱うか（5-1）？ → A: 完全ブロック（409エラーで拒否）。スタッフ用（`PUT /api/groups/:id`）・客用（`POST /customer/groups/:id/bill`）の両APIで同一挙動とする。専用エラーコード`ErrorCodes.Groups.UnservedItemsExist` / `ErrorCodes.Customer.UnservedItemsExist`（いずれも409）を新規追加する（グループ状態競合時の既存400応答とは別のエラーコード）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 会計依頼が不正な状態遷移・未提供注文の残存を許さない (Priority: P1)

客がテーブル端末から会計を依頼する操作と、ほぼ同時にホール/レジスタッフがそのテーブルの会計を確定させる操作が競合しても、会計確定（`closed`）が最終的な状態として維持される。会計依頼が確定処理を上書きしてしまうことはない。また、調理中・提供待ち（未提供）の注文明細が残っているグループに対する会計依頼（スタッフ用`PUT /api/groups/:id`・客用`POST /customer/groups/:id/bill`のいずれも）は、サーバー側で拒否される。

**Why this priority**: 会計確定後にステータスが「会計待ち」へ逆行すると、二重会計や売上集計の齟齬という金銭に直結する問題を招く。未提供の注文を残したまま会計状態に進めると、キッチンでの調理・提供漏れや「サービス未完了なのに会計扱い」という業務フロー上の矛盾が発生する。いずれもクライアント側のガードのみでは直接API呼び出し（客用QR画面、API誤用）で容易に回避されるため、サーバー側での検証が必須。

**Independent Test**:
- （状態競合）客用の会計依頼APIと、ホール/レジ側のグループ更新APIをほぼ同時に呼び出し、会計依頼側がグループを`closed`から`bill_requested`へ書き換えないことを確認する。
- （未提供注文）未提供（`pending`/`ready`）の注文明細を持つグループに対して、客用の会計依頼APIとスタッフ用のグループ状態更新APIをそれぞれ直接呼び出し、両方とも拒否される（会計待ち状態に遷移しない）ことを確認する。全明細が提供済み（`served`）または取消済み（`cancelled`）であるグループ、または注文明細が0件のグループでは、同じAPIが正常に会計待ち状態へ遷移できることも確認する。

この検証は他の2件（提供状況・コース適用）とは独立して行える。

**Acceptance Scenarios**:

1. **Given** テーブルのグループが`active`状態、**When** 会計依頼が処理される直前にホール/レジ操作で当該グループが`closed`に変わる、**Then** 会計依頼はグループを`bill_requested`に書き換えず、グループは`closed`のまま維持される。
2. **Given** テーブルのグループが`active`状態のまま他の変化がなく、未提供の注文明細もない、**When** 客が会計を依頼する、**Then** グループは`bill_requested`になり、関係者に通知される（現状と同じ成功挙動）。
3. **Given** アクティブなグループに未提供（`pending`）の注文明細が1件以上ある、**When** スタッフ用APIでグループを会計待ち状態に更新しようとする、**Then** サーバーは`409 groups.update.unserved_items_exist`で拒否し、グループの状態は`active`のまま変わらない。
4. **Given** アクティブなグループに提供待ち（`ready`）の注文明細が1件以上ある、**When** 客用APIで会計依頼を送信する、**Then** サーバーは`409 customer.bill.unserved_items_exist`で拒否し、グループの状態は`active`のまま変わらない。
5. **Given** アクティブなグループの全注文明細が提供済み（`served`）または取消済み（`cancelled`）である、または注文明細が0件、**When** スタッフ用API・客用APIのいずれかで会計依頼／状態更新を行う、**Then** グループは会計待ち状態に正常に遷移する。

### User Story 2 - キャンセル済みの注文が提供状況操作で復活しない (Priority: P1)

キッチン端末での「調理完了」「提供完了」操作と、ホール/レジでの「注文キャンセル」操作がほぼ同時に発生しても、キャンセルされた注文明細が`ready`や`served`へ復活することはない。

**Why this priority**: キャンセル済み・会計済みの注文が提供済み扱いに復活すると、提供状況表示や売上集計が実データと矛盾する。会計に影響しうるためHigh。

**Independent Test**: 同一注文明細に対して「注文キャンセル」APIと「調理完了」(`order:complete`)または「提供完了」(`order:serve`)イベントをほぼ同時に発行し、キャンセル済みの明細が`ready`/`served`に変化しないことを確認する。他の2件とは独立して検証できる。

**Acceptance Scenarios**:

1. **Given** 注文明細が`pending`状態、**When** `order:complete`の処理直前に当該明細が`cancelled`に変わる、**Then** 明細は`ready`に変化せず`cancelled`のまま維持される。
2. **Given** 注文明細が`ready`状態、**When** `order:serve`の処理直前に当該明細が`cancelled`に変わる、**Then** 明細は`served`に変化せず`cancelled`のまま維持される。
3. **Given** 注文明細が`pending`状態のまま他の変化がない、**When** キッチンが調理完了を操作する、**Then** 明細は`ready`になり関係者に通知される（現状と同じ成功挙動）。

---

### User Story 3 - コース適用・人数変更が最新のコース定義に基づいて処理される (Priority: P2)

店舗管理者がコースの価格・構成・紐づく飲み放題プランを編集する操作と、ホールスタッフがそのコースをテーブルに適用する（または適用済みコースの人数を変更する）操作がほぼ同時に発生しても、注文明細の作成・更新は処理完了時点で保存されているコース定義に基づいて行われる。

**Why this priority**: 会計金額の算出根拠がずれる問題だが、コース編集とコース適用が同時に発生する頻度は他2件より低く、影響度もMedium。

**Independent Test**: コース適用（またはコース人数変更）APIの処理中に、対象コースの価格・構成を変更するAPIをほぼ同時に呼び出し、生成・更新される注文明細が処理完了時点のコース定義（変更後の価格・構成）と一致することを確認する。他の2件とは独立して検証できる。

**Acceptance Scenarios**:

1. **Given** コースAが価格1000円で構成されている、**When** コース適用処理の実行中に管理者がコースAの価格を1200円に変更し、その変更が適用処理の完了より先に確定する、**Then** 適用処理が作成する定額課金明細の価格は1200円になる（1000円のまま作成されない）。
2. **Given** 適用済みコースの人数変更処理の実行中に、管理者が同コースの構成（コース料理の数量）を変更し、その変更が人数変更処理の完了より先に確定する、**Then** 人数変更処理が再計算する食事明細の数量は変更後の構成に基づく。
3. **Given** コース定義が処理中に変化しない通常時、**When** ホールスタッフがコースを適用する、**Then** 現状と同じ内容の注文明細が作成される（回帰なし）。

---

### Edge Cases

- 会計依頼の処理直前にグループが`closed`以外の別状態（削除・キャンセル等、存在すれば）に変わっていた場合も、`active`でなければ更新を行わない。
- `order:complete`/`order:serve`と同一明細への同時複数リクエスト（例: 2人のキッチンスタッフが同時に完了操作）が発生した場合、片方のみが成功し、もう片方は状態変化なしとなる。
- コース適用処理の実行中に対象コース自体が削除された場合（存在すれば）、適用処理は失敗として扱う。
- コース人数変更処理の実行中にグループのコース適用が解除された場合、人数変更処理は失敗として扱う（既存のグループ状態再検証と同様）。
- 通常時（競合が発生しない）は、3箇所とも現状と同じ応答内容・処理結果を維持する。
- 会計依頼の対象グループに、コース・飲み放題の定額課金明細（`menuItemId`を持たない自動生成明細）が未提供状態で残っている場合も、通常の注文明細と同様に未提供チェックの対象に含める。
- 会計依頼リクエストと、同時に発生する注文の提供完了操作（キッチン側の`order:serve`）が競合した場合、最終的な判定はサーバー側の検証タイミングでの実データに基づく（先に会計依頼が通れば以後の提供操作は通常通り可能、先に全明細が提供済みになれば会計依頼が通る）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 会計依頼処理（客用`POST /customer/groups/:id/bill`、スタッフ用`PUT /api/groups/:id`の`active`→`bill_requested`遷移）は、グループの状態確認とステータス更新を、両者の間に他の更新が割り込めない不可分な操作として行う。
- **FR-002**: 会計依頼処理は、不可分な操作の中で確認したグループの状態が`active`でない場合、ステータス更新を行わず、事前チェック時と同じエラー応答（客用: 400 / `BillRequestNotAllowed`、スタッフ用: 既存の状態遷移エラー）を返す。競合検知（事前チェック時は`active`だったが更新直前に他状態へ変わっていた場合）でも、この応答を再利用し専用のエラーコードは追加しない。
- **FR-002a**: 会計依頼処理は、FR-002と同じ不可分な操作の中で、対象グループに未提供（`pending`または`ready`）の`OrderItem`が1件でも存在する場合、ステータス更新を行わず、専用のエラー応答（客用: 409 / `customer.bill.unserved_items_exist`、スタッフ用: 409 / `groups.update.unserved_items_exist`）を返す。これはFR-002のグループ状態競合エラーとは別の理由によるものであり、別のエラーコードを用いる。
- **FR-002b**: 未提供チェック（FR-002a）は、コース・飲み放題の定額課金明細（`menuItemId`が`null`の自動生成明細）も通常の`OrderItem`と同じ`status`ライフサイクルを持つものとして対象に含める。
- **FR-002c**: 会計依頼処理は、対象グループの注文明細がすべて提供済み（`served`）・取消済み（`cancelled`）、または0件の場合は、従来どおり会計依頼／状態更新を許可しなければならない（FR-002aによる拒否対象外）。
- **FR-003**: `order:complete`イベント処理は、対象注文明細のステータス確認（`pending`であること）およびグループ・セッションの`closed`状態確認と、明細のステータス更新を、両者の間に他の更新が割り込めない不可分な操作として行う。
- **FR-004**: `order:serve`イベント処理は、対象注文明細のステータス確認（`ready`であること）およびグループ・セッションの`closed`状態確認と、明細のステータス更新を、両者の間に他の更新が割り込めない不可分な操作として行う。
- **FR-005**: `order:complete`/`order:serve`は、不可分な操作の中で確認した対象明細が前提条件（ステータス・グループ/セッションの状態）を満たさない場合、明細のステータス更新を行わない。この場合、既存の前提条件不一致時の挙動と同様に、呼び出し元クライアントへエラー通知は行わない（サイレントno-op）。
- **FR-006**: コース適用処理（`POST /:id/course`）は、注文明細の作成およびグループの`courseId`/`drinkPlanId`更新に使用するコース・飲み放題プランの情報を、グループの状態確認・更新と同じ不可分な操作の内部で取得したものに限定する（操作開始前に取得した値を使い回さない）。
- **FR-007**: コース人数変更処理（`PUT /:id/course`）は、注文明細の数量再計算に使用するコース情報を、グループの状態確認・更新と同じ不可分な操作の内部で取得したものに限定する（操作開始前に取得した値を使い回さない）。
- **FR-008**: 本フィーチャーの変更範囲は、指摘された3箇所（会計依頼、`order:complete`/`order:serve`、コース適用・人数変更）に加え、5-1統合分（会計依頼への未提供注文チェック、スタッフ用`PUT /api/groups/:id`を含む）に限定する。`docs/data-model/concurrency-notes.md`に記載の既存参考実装（`orders.ts`のキャンセル処理、`refreshToken.ts`のトークンローテーション、`unapplyCourse`）は変更対象に含めない。
- **FR-009**: 上記いずれの処理も、競合が発生しない通常時は、成功時のレスポンス内容・Socket.io通知内容・処理結果を現状から変更しない。
- **FR-010**: `unapplyCourse`（`backend/src/routes/groups.ts`）の既存コメントを、実装内容と一致するよう修正する（指摘5-2）。挙動自体は変更しない。

### Key Entities *(include if feature involves data)*

- **Group**: テーブル（客の来店グループ）の状態を表す。`status`（`active`/`bill_requested`/`closed`等）、適用中の`courseId`/`drinkPlanId`を持つ。会計依頼・コース適用/人数変更の対象。
- **OrderItem**: 個々の注文明細。`status`（`pending`/`ready`/`served`/`cancelled`）、価格・数量、所属する`Group`への参照を持つ。提供状況更新・コース適用/人数変更・未提供チェック（会計依頼）の対象。
- **Course**: コースメニューの定義。価格・構成する料理（`foodItems`）・紐づく`DrinkPlan`を持つ。コース適用/人数変更処理が参照する。
- **DrinkPlan**: 飲み放題プランの定義。価格・対象商品を持つ。コース適用処理が参照する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 会計確定（`closed`）済みのテーブルが会計依頼操作によって`bill_requested`へ逆行するケースが、競合を再現する検証で発生しなくなる。
- **SC-002**: キャンセル済みの注文明細が「調理完了」「提供完了」操作によって`ready`/`served`へ復活するケースが、競合を再現する検証で発生しなくなる。
- **SC-003**: コース適用・人数変更によって作成・更新される注文明細の価格・数量が、処理完了時点で保存されているコース・飲み放題プランの定義と常に一致する（古い定義に基づく不整合が、競合を再現する検証で発生しなくなる）。
- **SC-004**: 競合が発生しない通常操作について、3箇所とも既存の成功時レスポンス・通知内容に回帰がない。
- **SC-005**: 未提供の注文明細が残っているグループに対して、スタッフ用・客用のいずれのAPIを直接呼び出しても、会計待ち状態への遷移が100%拒否される。
- **SC-006**: 全明細が提供済み・取消済みのグループ、または注文明細が0件のグループでは、既存と同じ操作性で会計待ち状態への遷移が成功する（回帰なし）。

## Assumptions

- 対象範囲は指摘された3箇所（会計依頼、`order:complete`/`order:serve`、コース適用・人数変更）に、5-1統合分（会計依頼への未提供注文チェック）を加えたものに限定する。
- データベースはSerializable分離レベルのトランザクションをサポートする（既存のコース適用処理で使用実績があるため前提とする）。単一行の条件付き更新のみで完結する操作（`order:complete`/`order:serve`）はcompare-and-swap、複数行の作成・更新や別テーブルの集計を伴う操作（会計依頼＝未提供注文の集計、コース適用・人数変更＝参照系エンティティ再取得）はSerializableトランザクション内再検証というように、操作の性質に応じて手段を選ぶ（詳細は`plan.md`で確定する）。会計依頼はcompare-and-swapからSerializableトランザクション内再検証に変更する（未提供注文チェックが別テーブル`OrderItem`の集計であり、`updateMany`の`where`句だけでは表現できないため）。
- 未提供注文チェックの対象は`Group.status`が`active`の状態から`bill_requested`への遷移のみとし、`bill_requested → closed`（会計確定）の遷移や`bill_requested → active`（会計依頼取消）の遷移には影響しない。
- 本フィーチャーはバックエンドのデータ整合性保証が対象であり、フロントエンドの表示・UI変更は競合発生時のエラーハンドリングに必要な最小限にとどめる。
- 競合が発生する頻度は低い（同一リソースへの同時操作が稀なケース）ため、スループット等の性能要件は現状維持を許容範囲とする。
