# Feature Specification: セキュリティ境界の強化（CORS越境許可・レート制限のプロキシ配下対応）

**Feature Branch**: `001-security-boundary-hardening`

**Created**: 2026-07-19

**Status**: Draft

**Input**: User description: "設計レビュー（work/review-arch-2026-07-18.md）の指摘1-1（CORSがBASE_DOMAIN配下の全サブドメインを信頼し、テナント間・プラットフォーム管理者への越境攻撃の踏み台になりうる、Medium）と指摘1-2（本番のリバースプロキシ配下ではrequest.ipベースのログイン試行レート制限が機能しない可能性、Low）を1フィーチャーとして仕様化する。根本原因は別（CORS境界設計 vs プロキシ配下でのIP解決）だが、いずれもセキュリティ境界・攻撃面の堅牢化という共通テーマのため1フィーチャーにまとめる。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 1店舗の管理画面が侵害されても他店舗・プラットフォーム管理者へ被害が波及しない (Priority: P1)

現状、`storeA.<BASE_DOMAIN>` で実行されるスクリプトから `storeB.<BASE_DOMAIN>` や `admin.<BASE_DOMAIN>` へ認証情報付き（cookie送信あり）のリクエストを送ると、CORS設定がこれを許可してしまう。将来どこか1店舗の管理画面にXSSが見つかった場合、その1件だけで全店舗・プラットフォーム管理者まで攻撃が波及しうる。本機能は、あるオリジンから送信されたリクエストは、そのオリジンに対応するテナント（店舗またはプラットフォーム管理者）のAPIへのみ認証情報付きでアクセスできるようにし、テナント間・管理者への越境を防ぐ。

**Why this priority**: 現状XSS自体は見つかっていないが、CORS設定はテナント分離の最終防衛線の1つであり、ここが崩れていると単一の脆弱性が全店舗規模の被害に拡大しうる。設計レビューでMediumと判定された中でも影響範囲が広いため最優先。

**Independent Test**: `storeA.<BASE_DOMAIN>` をOriginとして `storeB.<BASE_DOMAIN>` のAPI（`credentials: include`）を直接呼び出し、CORSエラーで拒否されることを確認する。同様に `storeA.<BASE_DOMAIN>` から `admin.<BASE_DOMAIN>` のAPIへのアクセスも拒否されることを確認する。一方、`storeA.<BASE_DOMAIN>` から自分自身（`storeA.<BASE_DOMAIN>`）のAPIへのアクセスは従来どおり成功することを確認する。

**Acceptance Scenarios**:

1. **Given** リクエストのOriginが `storeA.<BASE_DOMAIN>`、**When** `storeB.<BASE_DOMAIN>` のAPIへ認証情報付きでリクエストする、**Then** CORSにより拒否される。
2. **Given** リクエストのOriginが `storeA.<BASE_DOMAIN>`、**When** `admin.<BASE_DOMAIN>` のAPIへ認証情報付きでリクエストする、**Then** CORSにより拒否される。
3. **Given** リクエストのOriginが `storeA.<BASE_DOMAIN>`、**When** `storeA.<BASE_DOMAIN>` 自身のAPIへリクエストする、**Then** 従来どおり許可される。
4. **Given** リクエストのOriginが `admin.<BASE_DOMAIN>`、**When** `admin.<BASE_DOMAIN>` 自身のプラットフォームAPIへリクエストする、**Then** 従来どおり許可される。

---

### User Story 2 - 本番運用でログイン試行レート制限が意図どおり機能する (Priority: P2)

本番環境（ロードバランサ・リバースプロキシ配下）では、サーバーが受け取る接続元IPは常にプロキシのIPになり、レート制限のキーが全クライアントで同一になってしまう。この結果、1人の攻撃者による大量ログイン失敗が、無関係な正規ユーザーのログインまで一緒にブロックしてしまう（可用性低下）。本機能は、プロキシ配下でも実際のクライアントIPを正しく解決し、レート制限が攻撃者個別に機能するようにする。

**Why this priority**: 可用性への影響はあるが、悪用には攻撃者が能動的に大量ログイン失敗を発生させる必要があり、影響範囲もUser Story 1より限定的（Low）。ただし本番運用の信頼性に直結するため対応する。

**Independent Test**: プロキシ配下を模したリクエスト（`X-Forwarded-For` ヘッダー付き）を異なる送信元IPを装って複数回送り、各IPのログイン試行回数が独立してカウントされる（あるIPの制限到達が他のIPに影響しない）ことを確認する。

**Acceptance Scenarios**:

1. **Given** 本番相当の設定（プロキシ配下を想定）、**When** `X-Forwarded-For` ヘッダーで異なるクライアントIPを持つログイン失敗リクエストがそれぞれ制限回数まで送られる、**Then** 各クライアントIPのレート制限は独立してカウントされ、あるIPの制限到達が他のIPのログイン試行を妨げない。
2. **Given** 本番相当の設定、**When** 同一クライアントIPからログイン失敗が制限回数を超えて送られる、**Then** そのIPからのログイン試行は既存どおりレート制限される。
3. **Given** 開発環境（プロキシなし、直接接続）、**When** ログイン試行が行われる、**Then** 既存どおりの挙動（直接の接続元IPに基づくレート制限）が維持される。

---

### Edge Cases

- `Origin` ヘッダーが存在しないリクエスト（同一オリジンのnavigationやサーバー間通信等）は、既存どおりCORSチェックの対象外として許可する。
- 解決できないHost（`resolveStoreContext` が店舗を特定できない、または `admin` でもない）に対するリクエストは、Originの許可判定において拒否側として扱う。
- プロキシ配下の設定を有効にした場合、開発環境（直接接続、プロキシなし）でクライアントの実際の接続元IPが誤って書き換えられないこと（`X-Forwarded-For` が存在しない場合は通常どおりソケットの接続元IPを使う）。
- `refreshToken.ts` に記録される監査用の `ipAddress` も、レート制限と同じ方法で解決したクライアントIPを使うようにする（本番で意味のある値になるようにするため）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、認証情報（cookie）付きのクロスオリジンリクエストを、リクエスト先のHostが表すテナント（店舗のサブドメイン、または`admin`）とOriginのホスト名が一致する場合にのみ許可しなければならない。
- **FR-002**: システムは、Originのホスト名がリクエスト先のHostと一致しない場合、テナント種別（店舗間、店舗→管理者、管理者→店舗のいずれであっても）を問わず、そのクロスオリジンリクエストを拒否しなければならない。
- **FR-003**: システムは、`Origin`ヘッダーが存在しないリクエスト（ブラウザ外からの呼び出し等）については、既存の挙動（許可）を維持しなければならない。
- **FR-004**: システムは、本番相当の環境（リバースプロキシ配下）で、ログイン試行のレート制限判定に使うクライアントIPを、プロキシが転送する実際のクライアントIP情報から解決しなければならない。
- **FR-005**: システムは、開発環境（プロキシなしの直接接続）では、レート制限判定に使うクライアントIPの解決方法を変更前と同じ挙動に保たなければならない（回帰なし）。
- **FR-006**: システムは、あるクライアントIPのログイン試行がレート制限に達しても、別のクライアントIPからのログイン試行に影響を与えてはならない。

### Key Entities *(include if feature involves data)*

- **Origin判定コンテキスト**: リクエストのOriginホスト名と、Hostから解決されたテナント（店舗のサブドメインまたは`admin`）の組。CORS許可判定に使う。
- **クライアントIP**: レート制限のキー、および監査ログ（`RefreshToken.ipAddress`）に記録される値。プロキシ配下か直接接続かによって解決方法が異なる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 店舗間・店舗からプラットフォーム管理者への認証情報付きクロスオリジンリクエストが、検証環境で100%拒否される。
- **SC-002**: 各テナント自身のオリジンからの認証情報付きリクエストは、既存と同じ成功率で処理される（回帰なし）。
- **SC-003**: 本番相当環境で、あるクライアントIPからの大量ログイン失敗が、別のクライアントIPのログイン試行成功率に影響を与えない。
- **SC-004**: 開発環境でのログイン試行レート制限の挙動（回数・時間窓）に変化がない。

## Assumptions

- 現状のコードベースには、あるサブドメイン（店舗またはadmin）のフロントエンドから別サブドメインのAPIへ、認証情報付きで正当にアクセスする必要のあるユースケースは存在しない（`plan.md`で実コードを確認し、もし存在する場合は本フィーチャーのスコープまたは設計を見直す）。
- 本番環境は単一の信頼できるリバースプロキシ/ロードバランサ（ECS想定）の配下で稼働し、その先のヘッダー（`X-Forwarded-For`等）は改ざんされない前提とする。プロキシを経由しない直接インターネットからのアクセスは本番構成上想定しない。
- レート制限用クライアントIPと監査ログ用クライアントIP（`refreshToken.ts`の`ipAddress`）は、同じ解決方法に統一する（両者の間で異なるIP解決ロジックを持たせない）。
- 本機能はバックエンドの設定・検証ロジックの変更が中心であり、フロントエンドの変更は不要と仮定する（既存のクロスサブドメイン呼び出しがない前提のため）。
